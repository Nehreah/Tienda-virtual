Resumen ejecutivo
Qué cambia en la versión 5.0 y por qué

La versión 5.0 conserva la ambición de nivel empresa del plan v4.0 y no recorta alcance. Lo que cambia es la
forma de construirlo: cada canal pasa a ser un módulo independiente que puede estar encendido, pausado
o apagado, el Excel se consolida como fuente de verdad del catálogo, y la negociación deja de ser una regla
de precios para convertirse en un motor comercial con escalera de concesiones e intercambios.

02 Principios rectores

Las reglas que guían cualquier decisión técnica o comercial

#

Principio

Consecuencia práctica

1

El núcleo no conoce los canales

Dominio y aplicación no importan ninguna librería de WhatsApp, Meta ni Mercado
Libre. Solo conocen el puerto ChannelPort.

2

Un canal apagado no afecta a los demás

Estados por canal, outbox por canal, circuit breaker por canal y pools de hilos
separados.

3

El LLM interpreta; el dominio decide

Gemini convierte texto en una intención estructurada. Nunca fija precios, aprueba
descuentos ni reserva stock.

4

El dinero interno nunca viaja donde no
debe

PM, costo, ganancia, ROI y margen no aparecen en DTOs públicos, prompts, logs ni
mensajes.

5

Excel manda sobre el catálogo; la BD
manda sobre lo operativo

Nombre, precios y descripción vienen del Excel. Reservas, ventas y stock vivo viven
en PostgreSQL y no se pisan al reimportar.

6

Todo evento externo es idempotente

Cada webhook se deduplica por externalEventId; cada envío usa clave de
idempotencia.

7

Cada regla comercial tiene su test de
frontera

Si una regla mueve dinero o stock, existe una prueba que ataca justo su límite.

8

Todo es observable y reversible

Cada decisión queda en auditoría; cada despliegue y cada catálogo se pueden
revertir.

Preguntas de revisión en cada pull request
Pregunta

Si la respuesta es «sí»…

¿Este cambio obliga a modificar el núcleo para soportar un canal
concreto?

Se rediseña: la diferencia debe vivir en el adaptador o en una
capacidad.

¿Algún dato interno (PM, costo, margen) puede llegar a un DTO, log,
prompt o mensaje?

Se bloquea el merge hasta añadir la prueba de fuga
correspondiente.

¿La operación se puede ejecutar dos veces y producir efectos distintos?

Se añade idempotencia y una prueba de repetición.

¿El texto de un cliente puede alterar una regla de precios o una
política?

Se mueve la decisión al dominio y se ignora el texto como
fuente de reglas.

¿Falla de forma segura si el LLM, la BD o el canal no responden?

Se define el modo degradado y se prueba.

Cómo se usan estos principios

No son un adorno: cada principio se traduce en una prueba automatizada, una regla de arquitectura o una alerta. Si un
principio no puede verificarse por máquina, se reescribe hasta que pueda.

Mecanismos que garantizan la independencia
• ChannelRegistry: descubre los módulos instalados y consulta el estado en channel_configs; solo enruta a los canales
ACTIVO o DEGRADADO.
• Capacidades en lugar de condicionales: TEXT, IMAGES, TEMPLATES, WINDOW_24H, PUBLISH. El núcleo adapta el
contenido a lo que el canal soporta.
• Aislamiento de fallos: pool de hilos, circuit breaker, límite de tasa y outbox propios por canal.
• Kill switch auditado: activar, pausar o apagar un canal queda registrado con usuario, hora y motivo.
• Health check periódico: valida credenciales, vencimiento de tokens y alcance de la API del canal.

Conflictos y casos límite
• Producto con reserva vigente que el Excel marca inactivo: la reserva se respeta y el conflicto aparece en el preview.
• Producto ausente del nuevo Excel: se marca inactivo (borrado lógico); nunca se elimina su historial.
• Producto VENDIDO en la BD que el Excel trae como ACTIVO: bloquea hasta que un usuario decida.
• Reimportar el mismo archivo (mismo hash) no crea una versión nueva.

Modos de ingreso y ida y vuelta
• Subida manual desde el dashboard (modo principal, Fase 4).
• Carpeta vigilada o sincronización programada (opcional): usa el mismo pipeline, sin atajos.
• Exportación de regreso: el sistema genera un Excel con el estado operativo (vendidos y reservados) para que el negocio
mantenga su archivo al día.
• Rollback de catálogo: cada versión se conserva y se puede reactivar con un clic y auditoría.

06 Motor de negociación

De una regla de precios a una estrategia comercial determinista

En v4.0 la negociación era un when con una zona ambigua entre PP y PM. En v5.0 esa zona se convierte en
una escalera de concesiones: el bot cede poco a poco, cada vez menos, y solo a cambio de algo. Es 100 %
determinista y configurable.

Principios de negociación aplicados
Principio

Cómo se implementa

Anclar alto y defender el valor

El bot habla de estado, garantía y disponibilidad antes de mencionar descuentos. El primer
precio es siempre PP.

Concesiones decrecientes

Cada paso cede menos que el anterior (30 %, 20 %, 15 %, 15 % del rango). Comunica que se
acerca al límite.

Nada gratis: intercambios

Salvo la cortesía inicial, cada nivel exige una contrapartida: pago inmediato, retiro, paquete o
cierre hoy.

El PM es un piso, no un objetivo

El piso automático (L4) queda por encima del PM. Entre L4 y PM decide una persona.

Escasez solo si es real

«Queda uno» se muestra únicamente cuando el stock disponible es 1.

NegotiationService · pseudocódigo ilustrativo

fun decide(p: Product, fin: Financials, offer: Money, earned: Int, policy: Policy): Decision {
val range = p.publishedPrice - fin.minimumPrice
// R = PP - PM
fun level(k: Int) = (p.publishedPrice - range * policy.ladder[k - 1]).roundUp(policy.rounding)
val floor = level(policy.ladder.size)
// L4: piso automatico
val current = level(earned)
// nivel ganado (>= 1)
return when {
!p.isNegotiable()
-> Decision.Reject(Reason.UNAVAILABLE)
offer >= p.publishedPrice -> Decision.Accept(p.publishedPrice)
offer >= current
-> Decision.Accept(offer)
offer >= floor
-> Decision.Counter(current, unlock = nextTrade(earned))
offer >= fin.minimumPrice -> Decision.Escalate(suggested = floor)
else
-> Decision.CounterBelowMin(current)
}
}

Defensas contra la manipulación
• El texto del cliente nunca modifica la política. Frases como «el dueño me dijo que…» se ignoran y se registran.

// duplicado: no se reprocesa
if (!processed.markIfNew(channel, event.externalEventId)) return@tx

outbox.enqueue(channel, reply)

}

Anexo D · Glosario
Términos usados en este documento

Término

Definición

PP

Precio Publicado: el precio visible para el cliente.

PM

Precio Mínimo: límite interno de negociación. Nunca se expone.

R

Rango de negociación: PP − PM.

L0–L4

Niveles de la escalera de concesiones. L4 es el piso automático.

Intercambio

Contrapartida que el cliente ofrece para desbloquear un nivel (pago inmediato, retiro, paquete, cierre
hoy).

Price realization

Precio de cierre dividido por el PP.

Outbox

Patrón que guarda los mensajes salientes en la misma transacción que la decisión, para enviarlos después
con reintentos.

Idempotencia

Propiedad por la cual repetir una operación no cambia el resultado.

DLQ

Dead-letter queue: cola de eventos que agotaron sus reintentos.

DTO

Data Transfer Object: estructura que define exactamente qué datos salen del sistema.

IDOR

Insecure Direct Object Reference: acceso indebido a recursos de otro usuario cambiando un identificador.

RBAC

Control de acceso basado en roles.

TTL

Tiempo de vida de una reserva u oferta antes de expirar.

ADR

Architecture Decision Record: registro breve de una decisión de arquitectura.

Guion dorado

Conversación de referencia que debe producir siempre el mismo resultado comercial.

Los plazos, los parámetros numéricos y los valores monetarios de este documento son referenciales y deben calibrarse
con datos reales. Las capacidades, permisos y políticas de WhatsApp, Meta, Mercado Libre, pasarelas de pago y Gemini
deben verificarse contra su documentación oficial vigente al implementar cada adaptador.
